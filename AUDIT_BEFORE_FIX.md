# PAIMANA Pre-Fix Technical Audit

Date: 2026-09-12  
Scope: repository source, tests, generated data, models, frontend bundles, and configuration.  
Method: read-only source/artifact inspection before implementation changes. Existing automated execution is recorded separately after the fixes; no metrics are invented here.

## Repository Inventory

- Python backend, feature engineering, training, packaging, API, scripts, and tests are present.
- React/Vite frontend is present with source JSON, public JSON, dashboard JSON, and a checked-in `dist` bundle.
- Four monthly snapshots are represented in the normalized panel: April-July 2026.
- Trained joblib files and multiple JSON/CSV result generations are checked in.
- No Docker/deployment manifest was found.
- `frontend/node_modules` had previously been committed and was removed in the last repository cleanup, but the source tree still contains a checked-in `dist` output that requires an explicit policy.

## Issue Severity

- **P0:** critical, scientifically invalid, security-breaking, or judge-breaking.
- **P1:** major correctness, reproducibility, or contract defect.
- **P2:** moderate quality, validation, or maintainability defect.
- **P3:** minor clarity or operational defect.

## P0 Issues

### P0-1: Production “early warning” models are mostly contemporaneous classifiers

- **File:** `backend/02_feature_engineering.py`, `backend/train_models.py`, `backend/06_package_risk_profiles.py`
- **Line/function:** `build_temporal_features`; `main`; `train_and_export_production_model`
- **Why it is wrong:** `is_cost_overrun` and `is_time_overrun` are labels derived from the same snapshot that supplies current progress, expenditure, revised cost, and revised completion information. The production cost/time models train on those current-state labels. Only forward time escalation is modeled, and forward cost escalation is not trained or packaged.
- **Impact:** The system cannot honestly claim that its primary scores predict a future event before it occurs. This is the central scientific mismatch with an early-warning product.
- **Recommended fix:** Define explicit T+1 targets with continuity and censoring rules, train forward cost and time models, keep current-state monitoring visibly separate, and downgrade claims where four snapshots cannot support a strong forecast.

### P0-2: Temporal target construction treats unknown future schedule outcomes as non-overruns

- **File:** `backend/02_feature_engineering.py`
- **Line/function:** `build_temporal_features`
- **Why it is wrong:** Shifted schedule labels are converted with `fillna(0)`. A future row with no observable revised completion date can therefore be treated as a known on-time outcome. `shift(-1)` also assumes the next row is the next calendar month without checking month continuity.
- **Impact:** Forward labels are misclassified and can bias model evaluation.
- **Recommended fix:** Preserve unknown/censored labels as missing, require the next observed month to equal T+1, and exclude unknown targets from training/evaluation.

### P0-3: The system claims calibrated probabilities without calibration

- **File:** `backend/train_models.py`, `README.md`, `frontend/src/views/MethodologyView.jsx`, `frontend/src/components/DemoModal.jsx`
- **Line/function:** `train_and_export_production_model`; model methodology displays
- **Why it is wrong:** Raw `XGBClassifier.predict_proba` output is called “Calibrated XGBoost.” There is no temporally separated calibration set, Platt/sigmoid calibration, isotonic calibration, reliability curve, ECE, or calibration metadata. Brier score alone does not prove calibration.
- **Impact:** Probability values and UI/model-card claims are scientifically unsupported.
- **Recommended fix:** Implement a temporal calibration procedure only if the data supports it; otherwise remove “calibrated” and present scores as uncalibrated model scores.

### P0-4: SHAP is claimed but never generated by the production model

- **File:** `backend/train_models.py`, `scripts/build_frontend_data.py`, `frontend/src/views/RiskIntelligenceView.jsx`, `results/project_risk_profiles_full.json`
- **Line/function:** feature importance export; driver packaging; `topShapDrivers`
- **Why it is wrong:** No source imports `shap` or calls `TreeExplainer`. Training exports XGBoost global feature importances, while the frontend hard-codes local impacts and checked-in profiles use legacy feature names.
- **Impact:** Explainability claims are fabricated/inconsistent and cannot defend a judge’s request to show the calculation for a specific prediction.
- **Recommended fix:** Generate local SHAP values from the exact inference model and feature row, store model/feature/dataset metadata and base value, and make the frontend consume only generated values. Otherwise remove SHAP claims.

### P0-5: Risk score and risk-band definitions diverge across production paths

- **File:** `backend/06_package_risk_profiles.py`, `backend/app.py`, `scripts/build_frontend_data.py`, frontend risk views
- **Line/function:** `calculate_priority_score`; `predict_scenario_risk`; project packaging
- **Why it is wrong:** The batch package, API, and frontend builder use different weights, inputs, scale transforms, and thresholds. The API omits forward escalation while the package includes it; the builder adds progress and a different cost scale.
- **Impact:** The same project can receive conflicting priority scores and bands depending on whether it is loaded from static JSON or scored through the API.
- **Recommended fix:** Create `backend/risk_scoring.py` as the only implementation, define prototype thresholds/weights, and test batch/API/frontend equivalence.

### P0-6: Scenario API feature construction is not training-compatible

- **File:** `backend/app.py`, `backend/02_feature_engineering.py`
- **Line/function:** `predict_scenario_risk`; `build_temporal_features`
- **Why it is wrong:** Training uses `np.log1p` but API uses `np.log10`; age semantics differ; group history inputs are hard-coded constants rather than calculated from a cutoff dataset; unknown categories and unrealistic values are not handled as OOD warnings.
- **Impact:** API probabilities do not represent the trained feature distribution and can be confidently wrong for absurd inputs.
- **Recommended fix:** Share feature definitions and preprocessing, calculate historical features from data available before the scenario cutoff, validate ranges/categories, and return structured OOD warnings.

### P0-7: Legacy frontend sends project data to an external AI endpoint

- **File:** `frontend/paimana_dashboard.jsx`
- **Line/function:** Anthropic message request handler
- **Why it is wrong:** The legacy dashboard sends project fields and driver data to `api.anthropic.com`, contradicting air-gapped/zero-external-API claims and lacking a controlled backend, authentication, or data-governance boundary.
- **Impact:** Potential disclosure of project data and an indefensible security claim.
- **Recommended fix:** Remove the external call or replace it with an explicitly optional, authenticated server integration; document that authentication is absent in the prototype.

## P1 Issues

### P1-1: Historical comparable lookup permits self-matches

- **File:** `backend/05_comparable_project_lookup.py`, `results/historical_comparables.csv`
- **Line/function:** candidate construction in `main`
- **Why it is wrong:** Earlier snapshots are filtered, but `comparable_project_code != project_code` is not enforced. A project can match its own earlier state while being presented as a distinct historical precedent.
- **Impact:** Similarity and precedent evidence are inflated and semantically misleading.
- **Recommended fix:** Exclude same project code, or explicitly label same-project history as prior state rather than a comparable project; test the invariant.

### P1-2: Arbitrary distance is labeled as “similarity %”

- **File:** `backend/05_comparable_project_lookup.py`, frontend comparable views
- **Line/function:** `similarity_pct = 100 / (1 + adjusted_dist)`
- **Why it is wrong:** Euclidean distance after mixed-feature preprocessing has no validated percentage interpretation, and domain boosts alter it ad hoc.
- **Impact:** A value such as 95% falsely implies that 95% of characteristics match.
- **Recommended fix:** Expose distance and rank, or document/validate a bounded similarity normalization and call it a similarity score.

### P1-3: Generated artifacts have no common model/feature/dataset manifest

- **File:** `backend/models/*`, `results/*.json`, `scripts/build_frontend_data.py`, `run_pipeline.py`
- **Line/function:** artifact load/write paths
- **Why it is wrong:** Multiple model generations and duplicate profile/evaluation files are loaded without model version, feature version, dataset hash, package versions, training cutoff, or generation timestamp. `run_pipeline.py` does not regenerate every artifact that the frontend builder consumes.
- **Impact:** Checked-in outputs can be mutually incompatible and the claimed pipeline is not reproducible.
- **Recommended fix:** Add a manifest and metadata to all generated artifacts, make the pipeline generate them in dependency order, and fail on mixed versions.

### P1-4: Active frontend is static, despite live/real-time wording

- **File:** `frontend/src/services/dataService.js`, `frontend/src/data/paimana_data.json`, `backend/app.py`, README/UI text
- **Line/function:** data loading and API endpoints
- **Why it is wrong:** The active React app imports bundled static JSON and does not call FastAPI. The API exists as a separate service, while wording implies a live monitoring system.
- **Impact:** Users may believe dashboard values are live when they are precomputed.
- **Recommended fix:** Either integrate the frontend with the API or accurately call the UI a precomputed analytical dashboard with FastAPI scenario inference.

### P1-5: API alert filters use different field names from generated alerts

- **File:** `backend/app.py`, `scripts/build_frontend_data.py`
- **Line/function:** `get_alerts`; alert record generation
- **Why it is wrong:** API filters `level` and `type`, while generated records use `severity` and `risk_type`.
- **Impact:** Filters silently fail and return incorrect alert subsets.
- **Recommended fix:** Establish one schema and add API contract tests.

### P1-6: Historical risk is fabricated with a decay factor

- **File:** `scripts/build_frontend_data.py`
- **Line/function:** monthly history generation
- **Why it is wrong:** Current July risks are multiplied by a month-dependent decay factor and presented as historical model scores. They are not independently inferred from each snapshot.
- **Impact:** The trend visualization claims evidence that was never generated.
- **Recommended fix:** Re-score each historical snapshot with cutoff-safe features, or show observed telemetry only and rename the chart.

### P1-7: Data validation does not fail on critical schema/quality violations

- **File:** `backend/01_extract_pdfs.py`, `backend/02_feature_engineering.py`, `tests/test_data_pipeline.py`
- **Line/function:** extraction/cleaning and tests
- **Why it is wrong:** Invalid dates/numerics are coerced to missing, malformed extraction rows can be skipped, and duplicate project-month keys, missing IDs, date ordering, revised-cost relationships, category validity, and expenditure/progress consistency are not comprehensively validated.
- **Impact:** Silent corruption can reach feature generation and models.
- **Recommended fix:** Add a validation stage producing `data_quality_report.json`; fail on critical violations and report non-critical warnings.

### P1-8: Temporal evaluation has only four snapshots and project overlap is not disclosed consistently

- **File:** `backend/train_models.py`, `results/model_evaluation_report.json`, tests/docs
- **Line/function:** `run_temporal_benchmark`; production holdout
- **Why it is wrong:** Walk-forward splits are chronological, but the same projects appear in train and later snapshots. Four monthly snapshots do not support broad unseen-project or long-horizon claims, and active report artifacts use inconsistent sample sizes/cutoffs.
- **Impact:** Metrics can be overstated as general forecasting performance.
- **Recommended fix:** Clearly distinguish monitoring validation from unseen-project generalization, use only supported horizons, report positive counts and limitations, and regenerate reports from the active pipeline.

### P1-9: Existing tests validate stale committed artifacts rather than source-to-artifact behavior

- **File:** `tests/test_leakage.py`, `tests/test_models.py`, `tests/test_data_pipeline.py`
- **Line/function:** all tests
- **Why it is wrong:** Tests mostly load checked-in CSV/JSON/joblib files and assert broad thresholds. They do not rebuild features, verify feature parity, calibration, target censoring, artifact metadata, risk formula equivalence, comparable exclusion, or frontend build.
- **Impact:** Broken source code can pass while stale artifacts mask regressions.
- **Recommended fix:** Add focused unit/integration tests that build or fixture the relevant slices and test contracts.

### P1-10: Python dependency versions are not reproducible

- **File:** `requirements.txt`, repository root
- **Line/function:** dependency specification
- **Why it is wrong:** Requirements use ranges and omit Python version and key runtime packages such as FastAPI, Uvicorn, and SHAP if those are required after repair.
- **Impact:** Model serialization and training results may differ across environments.
- **Recommended fix:** Add an exact `requirements-lock.txt` generated from the execution environment and document Python version and install commands.

## P2 Issues

### P2-1: Model serialization files are opaque and duplicated

- **File:** `backend/models/`, `backend/03_train_cost_overrun_model.py`, `backend/04_train_time_overrun_model.py`, `backend/train_models.py`
- **Why it is wrong:** Standalone training scripts and the main training script use different model/preprocessing configurations, but filenames do not distinguish generations or schemas.
- **Impact:** A future run may load a model with the wrong feature contract.
- **Recommended fix:** Retire or archive unused training paths, use a single trainer, and write metadata beside each model.

### P2-2: Portfolio metrics are mislabeled as probabilities

- **File:** `scripts/build_frontend_data.py`, `frontend/src/views/OverviewView.jsx`
- **Why it is wrong:** `cost_risk_rate_pct` and `schedule_risk_rate_pct` are thresholded project proportions, not mean predicted probabilities.
- **Impact:** UI users can misinterpret portfolio rates as calibrated probabilities.
- **Recommended fix:** Rename them to threshold-exceedance rates and compute/display mean probability separately if needed.

### P2-3: Frontend contains hard-coded metric and driver fallbacks

- **File:** `frontend/src/views/RiskIntelligenceView.jsx`, `scripts/build_frontend_data.py`
- **Why it is wrong:** Fixed rates, fallback AUC/Brier values, and hard-coded driver impacts can survive artifact changes.
- **Impact:** UI can display unsupported results without an error.
- **Recommended fix:** Require versioned generated data and render an explicit unavailable state when fields are absent.

### P2-4: Multiple duplicate data surfaces can drift

- **File:** `frontend/src/data/paimana_data.json`, `frontend/public/data/paimana_data.json`, `frontend/dist/data/paimana_data.json`, `frontend/dashboard_data.json`, legacy dashboard
- **Why it is wrong:** No checksums or consistency test identifies which is authoritative; observed project counts and schemas differ.
- **Impact:** Different entry points can show different portfolios.
- **Recommended fix:** Define one generated source, copy only as part of the build, and add checksum/schema consistency checks.

### P2-5: Date semantics are inconsistent or under-documented

- **File:** `backend/02_feature_engineering.py`, `backend/app.py`, README
- **Why it is wrong:** Training computes project age from `start_date`, while API descriptions say since approval; year arithmetic is approximated by integer division.
- **Impact:** Scenario features do not mean the same thing as training features.
- **Recommended fix:** Define approval/start/target/revised/reporting dates and use calendar month arithmetic consistently.

### P2-6: Forward target coverage and censoring are not reported by class/horizon

- **File:** `backend/02_feature_engineering.py`, `backend/train_models.py`, results reports
- **Why it is wrong:** Counts of known targets and positive/unknown/censored examples are not a required artifact, and only T+1 is effectively used.
- **Impact:** Class imbalance and evidence for early warning cannot be judged.
- **Recommended fix:** Report known/unknown/positive counts per month and horizon; do not add unsupported T+3/T+6 claims.

### P2-7: CORS and operational defaults are unsafe

- **File:** `backend/app.py`, `run_pipeline.py`
- **Why it is wrong:** CORS allows all origins with credentials, and documented execution binds/reloads broadly. There is no authentication, rate limiting, or production transport guidance.
- **Impact:** Unsafe deployment posture for institutional data.
- **Recommended fix:** Explicit localhost origins for development, configurable trusted origins, no credentials with wildcard origins, and clear prototype/authentication limitations.

### P2-8: API metadata is hard-coded

- **File:** `backend/app.py`
- **Why it is wrong:** Snapshot month and project count are fixed in root/health responses rather than derived from loaded artifacts.
- **Impact:** API can report false operational state after regeneration.
- **Recommended fix:** Derive metadata from the authoritative generated dataset and manifest.

## P3 Issues

### P3-1: Parser relies on fragile PDF table assumptions

- **File:** `backend/01_extract_pdfs.py`
- **Why it is wrong:** Extraction depends on positional rows, exact table text, and heuristic labels without fixture tests or extraction-quality reporting.
- **Impact:** Source-format changes can silently reduce or distort input data.
- **Recommended fix:** Add parser fixtures, row-level error reporting, and schema validation after extraction.

### P3-2: `dist` is checked in without a documented release policy

- **File:** `frontend/dist/`
- **Why it is wrong:** Generated build output can become stale while source changes; clean-build requirements normally regenerate it.
- **Impact:** Users may run a different frontend than source code describes.
- **Recommended fix:** Either exclude `dist` and build it in deployment, or explicitly version and verify it as a release artifact.

### P3-3: Policy wording may imply government authority without source citations

- **File:** `scripts/build_frontend_data.py`, frontend recommendation views, README
- **Why it is wrong:** Recommendations mention MoSPI/Expenditure Department, empowered committees, and liquidated damages without a rule/source/section mapping.
- **Impact:** Recommendations can be mistaken for official policy advice.
- **Recommended fix:** Create `POLICY_RULE_SOURCES.md`; verify citations or label each as a prototype recommendation based on monitoring best practices.

2. Correct forward target continuity and censoring; separate current monitoring from future prediction.

4. Add canonical risk scoring and API feature/OOD handling.
5. Remove fabricated history and self-matches; define distance semantics.
6. Regenerate models/results/frontend data from one pipeline.
7. Add data, ML, business, comparable, API, integration, and frontend build tests.
